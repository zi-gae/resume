# 시나리오 기반 질문

### Q1. 프로덕션에서 갑자기 에러율이 급증하면 어떻게 대응하나요?
> **출제 의도**: 장애 대응 프로세스 및 우선순위 판단
>
> **경력 연관**: Datadog/Sentry 운영 경험

<details>
<summary><b>✅ 답변</b></summary>

**즉각 대응 (5분 이내)**:
1. **Datadog/Sentry 확인**: 에러 메시지, 영향 범위(사용자 수/비율), 발생 시점 확인
2. **최근 배포 확인**: 에러 발생 시점과 최근 배포 시점이 일치하면 배포 원인 가능성 높음
3. **롤백 판단**: 사용자 영향이 크면 즉시 롤백 (Blue-Green이면 5분 이내)

**원인 분석 (30분 이내)**:
1. Sentry 스택트레이스 + 브레드크럼으로 재현 경로 파악
2. Datadog RUM에서 해당 시간대의 사용자 세션 리플레이 확인
3. API 에러인 경우 백엔드 팀과 협업하여 서버 로그 확인

**재발 방지**:
1. 근본 원인 수정 후 테스트 케이스 추가
2. Lighthouse CI / E2E 테스트에 해당 시나리오 포함
3. 장애 회고 문서 작성 (타임라인, 원인, 해결, 재발 방지책)

**실제 경험**: 마이리얼트립에서 결제 플로우의 로컬스토리지 기반 상태 훅이 탭 간 동기화되지 않아 결제 이탈이 발생한 사례. Sentry에서 에러는 아니지만 GA 퍼널에서 이탈률 급증을 감지하여 문제를 발견했습니다.

</details>

### Q2. 성능이 매우 느린 페이지를 최적화해달라는 요청을 받았을 때, 어떤 순서로 접근하나요?
> **출제 의도**: 체계적 성능 최적화 프로세스
>
> **경력 연관**: 전체 성능 최적화 경험

<details>
<summary><b>✅ 답변</b></summary>

**Step 1. 측정 (Measure First)**:
- Lighthouse로 Performance 점수, LCP, FID, CLS 확인
- WebPageTest로 실제 네트워크 환경에서의 waterfall 분석
- Chrome DevTools Performance 탭으로 렌더링 병목 구간 확인
- Datadog RUM으로 실제 사용자 데이터(Real User Metrics) 확인

**Step 2. 원인 분류**:

| 카테고리 | 진단 도구 | 일반적 원인 |
|---------|----------|------------|
| 네트워크 | Network 탭, WebPageTest | 큰 번들, 불필요한 API 호출, CDN 미사용 |
| 렌더링 | Performance 탭, Profiler | 불필요한 리렌더링, 긴 태스크(Long Task) |
| 리소스 | Coverage 탭 | 미사용 CSS/JS, 최적화되지 않은 이미지 |

**Step 3. 우선순위 결정 (ROI 기준)**:
- 적은 노력으로 큰 개선: 이미지 최적화, 코드 스플리팅, CDN 캐시
- 중간 노력으로 중간 개선: React.memo, useMemo, 가상 스크롤
- 큰 노력으로 큰 개선: 아키텍처 변경, SSR 도입

**Step 4. 개선 + 검증**:
- 변경 전후를 동일 조건에서 측정하여 정량적 개선 확인
- Lighthouse CI로 PR 단위로 성능 회귀 방지

</details>

### Q3. 디자인 시스템의 Breaking Change를 다수 팀에 전파해야 할 때 어떻게 하나요?
> **출제 의도**: 라이브러리 운영과 커뮤니케이션 전략
>
> **경력 연관**: 마이리얼트립 디자인시스템

<details>
<summary><b>✅ 답변</b></summary>

**전파 프로세스**:

1. **사전 공지 (2주 전)**:
   - 슬랙 채널에 Breaking Change 예고 공지
   - CHANGELOG에 상세 마이그레이션 가이드 포함
   - 이전 버전과 새 버전의 API 차이를 비교 테이블로 정리

2. **전환 기간 (2주)**:
   - 이전 버전을 deprecation 경고와 함께 유지
   - 마이그레이션 PR 예시를 제공하여 각 팀이 참고
   - 마이그레이션 중 발생하는 이슈를 즉시 대응

3. **완료 후**:
   - 이전 버전 제거
   - 마이그레이션 결과 확인 (빌드, 테스트 통과 여부)

**자동화 지원**:
- Codemod 스크립트 제공: 기계적으로 변환 가능한 부분은 자동 변환 스크립트를 제공
- 예: `<Button type="primary">` → `<Button variant="primary">`
- `jscodeshift`로 AST 기반 코드 변환 스크립트 작성

**교훈**: Breaking Change는 기술적 문제보다 커뮤니케이션 문제입니다. 충분한 사전 공지와 마이그레이션 지원이 없으면 팀에서 디자인 시스템 업데이트 자체를 꺼리게 됩니다.

</details>

### Q4. 새로운 팀에 합류했을 때 코드베이스를 파악하는 전략은?
> **출제 의도**: 적응력과 코드 분석 역량
>
> **경력 연관**: 마이리얼트립 렌터카/숙소 인수

<details>
<summary><b>✅ 답변</b></summary>

**1주차 - 전체 그림 파악**:
1. `package.json`으로 기술 스택과 주요 의존성 확인
2. 디렉토리 구조로 아키텍처 패턴 파악 (Feature-based? Layer-based?)
3. README, 위키 등 문서 확인
4. CI/CD 파이프라인으로 빌드/배포 프로세스 이해
5. 서비스를 직접 사용하면서 사용자 플로우 체험

**2주차 - 코드 레벨 이해**:
1. 라우팅 설정에서 출발하여 주요 페이지의 코드를 탑다운으로 읽기
2. 공통 유틸/훅/컴포넌트부터 파악 (가장 많이 import되는 모듈)
3. Git 히스토리에서 최근 변경 빈도가 높은 파일(핫스팟) 확인 → 활발히 개발 중인 영역
4. Sentry/Datadog에서 현재 발생 중인 에러/이슈 확인 → 기존 문제 파악

**빠른 기여 시작**:
- 작은 버그 수정이나 문서 보완으로 첫 PR 생성
- PR 리뷰를 받으면서 팀의 컨벤션과 기대 수준을 파악
- 질문은 "내가 이해한 바가 맞는지" 확인하는 형태로 (조사 후 질문)

**마이리얼트립 렌터카/숙소 인수 경험**: 담당자가 없는 코드를 2주간 분석한 후 리스크 우선순위 로드맵을 수립하여 팀에 공유. 가장 빈번한 Sentry 에러부터 순차적으로 해결.

</details>

### Q5. 기존 팀원이 선호하는 기술과 본인이 제안하는 기술이 다를 때 어떻게 설득하나요?
> **출제 의도**: 기술적 커뮤니케이션과 설득력
>
> **경력 연관**: 전체 경력

<details>
<summary><b>✅ 답변</b></summary>

**원칙**: 기술은 "취향"이 아닌 "근거"로 선택해야 합니다.

**접근 방법**:

1. **문제 합의**: "어떤 기술을 쓸까?"보다 "어떤 문제를 풀어야 하나?"에 먼저 합의
2. **객관적 비교**: 두 기술을 동일한 기준(성능, 러닝 커브, 유지보수성, 커뮤니티)으로 비교하는 표를 작성
3. **PoC 제시**: 말보다 코드가 설득력이 있으므로, 두 기술로 동일한 기능을 PoC로 구현하여 비교
4. **리스크 인정**: 제안하는 기술의 단점도 솔직하게 공유. 장점만 이야기하면 신뢰 하락
5. **점진적 도입 제안**: 전면 전환이 아닌 일부에 먼저 적용하여 검증 후 확대

**실제 사례 - Redux → React Query**:
- 팀원들이 Redux에 익숙하여 React Query 전환에 회의적
- 신규 기능 하나에 React Query를 적용하여 코드 감소와 DX 개선을 직접 보여줌
- 2개월간 Redux와 공존하면서 자연스럽게 React Query의 장점을 체험
- 최종적으로 팀 합의하에 서버 상태를 React Query로 전환

**교훈**: 설득은 한 번의 미팅이 아닌 지속적인 과정입니다. PoC → 부분 적용 → 결과 공유 → 전면 확대의 단계를 거쳐야 팀 전체가 납득합니다.

</details>

### Q6. 프론트엔드 개발자로서 백엔드 팀과의 API 설계 협업은 어떻게 하나요?
> **출제 의도**: 크로스 팀 협업 역량
>
> **경력 연관**: 전체 경력

<details>
<summary><b>✅ 답변</b></summary>

**API 설계 협업 프로세스**:

1. **요구사항 정의**: 프론트엔드에서 필요한 데이터를 화면 기준으로 정리하여 백엔드에 전달
2. **API 스펙 리뷰**: 백엔드가 초안을 작성하면, 프론트엔드에서 사용성 관점으로 리뷰
   - 한 화면에 필요한 데이터가 여러 API에 분산되어 있으면 BFF 또는 API 통합 요청
   - 페이지네이션 방식, 정렬 파라미터, 에러 응답 형식 등 합의
3. **Mock API 선행 개발**: API 스펙이 확정되면 MSW(Mock Service Worker)로 목 서버를 구성하여 프론트엔드 개발을 병렬로 진행

**주로 요청하는 것들**:
- 일관된 에러 응답 형식 (error code, message, detail)
- 목록 API에 totalCount 포함 (프론트엔드 페이지네이션에 필요)
- 필터/정렬 파라미터의 네이밍 컨벤션 통일
- null과 빈 문자열, 0의 의미 구분 명확화

**갈등 사례와 해결**: 백엔드에서 한 API에서 모든 데이터를 반환하면 응답 크기가 커지고, 프론트엔드에서 원하는 만큼만 호출하면 API 수가 많아지는 트레이드오프. BFF 패턴으로 프론트엔드용 API를 별도로 구성하여 양쪽 만족.

</details>

### Q7. 접근성(a11y)을 어떻게 고려하나요?
> **출제 의도**: 접근성 인식과 실무 적용
>
> **경력 연관**: 이그나이트 기아 인증 중고차 (WCAG 2.1 AA, 67→91)

<details>
<summary><b>✅ 답변</b></summary>

**기아 인증 중고차에서의 접근성 개선 (67→91점)**:

1. **시맨틱 HTML**: `<div>` 남발 대신 `<nav>`, `<main>`, `<article>`, `<button>` 등 적절한 태그 사용
2. **ARIA 속성**: 커스텀 컴포넌트에 `role`, `aria-label`, `aria-expanded` 등 ARIA 속성 추가
3. **키보드 네비게이션**: Tab 순서 보장, Enter/Space로 버튼 동작, Escape로 모달 닫기
4. **색상 대비**: WCAG 2.1 AA 기준(4.5:1 이상) 충족. 디자이너와 협업하여 대비가 낮은 색상 조합 수정
5. **대체 텍스트**: 모든 이미지에 의미 있는 `alt` 텍스트 추가. 장식용 이미지는 `alt=""`

**자동화 도구**:
- Lighthouse Accessibility 감사를 CI에 포함
- `eslint-plugin-jsx-a11y`로 빌드 시 접근성 문제 감지
- 스크린 리더(VoiceOver) 수동 테스트 병행

**결과**: Lighthouse 접근성 점수 67 → 91, 글로벌 서비스에서 법적 요건(ADA, WCAG) 충족.

</details>

### Q8. 모노레포 환경에서 팀이 커질수록 빌드 속도가 느려지고 패키지 간 의존성 관리가 어려워질 때 어떻게 접근하나요?
> **출제 의도**: 모노레포 운영 경험과 기술적 판단력
>
> **경력 연관**: Ignite Turborepo 모노레포, MRT Frontend libs 순환참조 해결

<details>
<summary><b>✅ 답변</b></summary>

**문제 진단 순서**:

1. **빌드 병목 파악**: `turbo run build --profile`로 태스크별 소요 시간 측정, 캐시 히트율 확인
2. **의존성 그래프 시각화**: `turbo run build --graph`로 패키지 간 의존 관계 파악
3. **순환 참조 탐지**: Barrel 파일(`index.ts`) 간 순환 참조는 모듈 해석 인스턴스를 무한 생성시켜 빌드/테스트 시간을 폭증시킴

**빌드 속도 개선 전략**:

- **Remote Cache 활성화**: Turborepo Remote Cache(Vercel 또는 자체 서버)로 CI 환경 간 캐시 공유
- **태스크 의존성 최적화**: `turbo.json`의 `dependsOn` 재검토, 불필요한 직렬 실행을 병렬로 전환
- **Barrel 파일 제거**: `index.ts`에서 전체 re-export 대신 직접 import로 전환 → 모듈 해석 범위 축소

**의존성 관리 전략**:

- 패키지를 `shared/ui`, `shared/utils`, `shared/hooks`처럼 역할 단위로 분리, 단방향 의존성 원칙 적용
- `eslint-plugin-import`의 `no-cycle` 룰로 빌드 타임에 순환 참조 감지
- 브랜드별로 공통 컴포넌트를 공유하되, 브랜드 특화 로직은 각 앱 레이어에서 override

**실제 경험 - MRT Frontend libs**:
- Barrel 파일 간 순환 참조로 Lint + Jest가 12분 이상 소요되는 CI 병목 발생
- `barrel 파일 제거 + 직접 import` 전환으로 12분 → 5분으로 단축

</details>

### Q9. 글로벌 서비스에서 i18n 번역 누락 이슈가 반복적으로 발생할 때 어떻게 근본적으로 해결하나요?
> **출제 의도**: 자동화 설계 역량과 반복 문제 해결 접근법
>
> **경력 연관**: Ignite i18n 운영 자동화 (번역 누락 0건 유지)

<details>
<summary><b>✅ 답변</b></summary>

**문제 구조 파악**:
- 번역 누락은 보통 "개발자가 키를 추가했지만 번역 시트에 반영을 빠뜨리는" 프로세스 갭에서 발생
- 사람이 기억에 의존하는 한 반복됨 → 자동화로 구조적으로 막아야 함

**자동화 파이프라인 설계**:

1. **번역 키 누락 감지 CI**: PR 시 코드에서 사용 중인 i18n 키를 정적 분석하여 번역 파일에 없는 키를 감지, 빌드 실패 처리
2. **번역 시트 자동 동기화**: 새 키가 감지되면 Google Sheets API를 통해 번역 시트에 자동으로 행 추가 (번역 담당자가 채울 수 있도록)
3. **배포 전 검증**: 번역 완료 여부를 배포 파이프라인의 Gate 조건으로 설정

**런타임 안전망**:
- `i18next`의 `missingKeyHandler`로 누락된 키를 Datadog/Sentry에 리포팅
- 기본값(fallback) 설정으로 누락 키가 화면에 raw key로 노출되지 않도록 처리

### Q10. MSA 환경에서 여러 도메인의 인증 토큰을 프론트엔드에서 다뤄야 할 때 어떻게 설계하나요?
> **출제 의도**: 복잡한 인증 아키텍처 이해도와 문제 해결력
>
> **경력 연관**: Ignite 이중 액세스 토큰 구조, Mutex 패턴, Datadog 99.7% 인증 성공률

<details>
<summary><b>✅ 답변</b></summary>

**문제 상황**:
- MSA 환경에서 도메인별로 인증 방식과 요청 헤더가 다른 경우, 단일 토큰으로 모든 API를 처리할 수 없음
- 토큰 갱신 중 동시 요청이 몰리면 중복 갱신 요청과 Race Condition 발생

**이중 토큰 설계**:
- **Parent 토큰 (A)**: 메인 인증 서버에서 발급, 유저 세션 대표
- **Child 토큰 (B)**: A 토큰으로 도메인별 서비스 토큰을 발급받는 구조
- A 만료 시 B도 자동 무효화 → A 갱신 → B 재발급 → 대기 요청 재시도 순서 보장

**Race Condition 방지 - Mutex 패턴**:
```
토큰 갱신 중 = Mutex Lock 획득
→ 이후 동시 요청들은 Lock 해제까지 Queue에서 대기
→ 갱신 완료 후 일괄 재시도
```

**통합 HTTP 클라이언트 구현**:
- 도메인별로 다른 헤더 값을 하나의 클라이언트에서 관리
- Interceptor에서 요청 URL 기반으로 올바른 토큰과 헤더를 자동 주입

**결과 - Ignite**:
- 토큰 갱신 중 동시 요청 최대 50건 처리
- 인증 성공률 99.7% (Datadog APM 측정)

</details>

### Q14. 프론트엔드에서 GDPR/CCPA 같은 개인정보 보호 규정을 어떻게 대응하나요?

<summary><b>✅ 답변</b></summary>

**GDPR/CCPA가 프론트엔드에 미치는 영향**:
- 동의 없는 트래킹 쿠키/분석 도구 실행 금지
