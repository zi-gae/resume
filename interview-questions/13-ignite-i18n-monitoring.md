### Q1. i18n 운영에서 번역 키 누락 감지 CI를 어떻게 구축했나요?
> **출제 의도**: i18n 운영 자동화와 CI 품질 게이트 설계 역량
>
> **경력 연관**: 이그나이트 딜러포탈

<details>
<summary><b>✅ 답변</b></summary>

**배경**: 전세계 딜러 포탈이라 현대/기아/제네시스 3개 브랜드, 40여개국 언어를 지원했습니다. 개발자가 새 UI 문구를 추가하면서 번역 키는 코드에 삽입했지만, 번역 시트에 해당 키를 추가하지 않은 채 배포되어 사용자에게 키 문자열이 그대로 노출되는 문제가 반복됐습니다.

**CI 파이프라인 구성**:

```
PR 생성
└── CI Stage: i18n Key Validation
    ├── 코드에서 번역 키 추출 (grep/AST 파싱)
    ├── 번역 JSON 파일에서 등록된 키 목록 추출
    ├── 차집합 계산 → 누락 키 목록 출력
    └── 누락 키 존재 시 파이프라인 실패 + PR 코멘트 자동 생성
```

**번역 시트 자동 업데이트**:
- 새 키가 머지되면 Google Sheets API로 번역 시트에 해당 키 행을 자동 추가
- 번역가에게 Slack 알림으로 신규 번역 요청 전달
- 번역 완료 후 시트 → JSON 자동 동기화 스크립트로 PR 자동 생성

**결과**: 배포 후 번역 누락 건수 0건 유지.

</details>

**꼬리 질문**:
- 번역 키를 코드에서 어떻게 추출했나요? (동적 키 처리)
- 번역 시트와 코드 간 sync lag은 어떻게 처리했나요?
- 40개국 언어를 지원하면서 특히 어려웠던 케이스는?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **동적 키 추출**: 정적 키(`t('vehicle.list.title')`)는 grep으로 추출하지만, 동적 키(`t(\`vehicle.status.${status}\`)`)는 템플릿 리터럴 패턴으로 추출이 불완전합니다. 동적 키는 `t()` 호출 위치를 마킹하고, 가능한 값(status enum)을 타입에서 추출하여 예상 키 목록을 생성했습니다. 동적 키가 많은 영역은 별도 예외 목록으로 관리하고 코드 리뷰에서 직접 검증했습니다.

- **Sync Lag 처리**: 번역 시트 업데이트는 머지 직후 비동기로 실행되어, 번역가가 작업하는 동안 수일이 걸릴 수 있습니다. 이 기간에 다른 언어로 배포되면 누락이 생기므로, 번역이 완료되지 않은 언어는 fallback 언어(영어)를 자동으로 표시하는 i18n fallback 설정을 적용했습니다. 번역 완료율을 대시보드로 모니터링하여 특정 언어의 번역 지연이 심하면 알림이 오도록 했습니다.

- **어려웠던 케이스**: 아랍어(RTL) 지원이 가장 복잡했습니다. 단순히 번역 텍스트를 교체하는 것 외에 `dir="rtl"` 속성 적용, Flexbox/Grid 방향 미러링(`margin-left` → `margin-right`)이 필요했습니다. CSS의 논리 속성(`margin-inline-start`, `padding-inline-end`)으로 방향에 중립적인 스타일을 사용하도록 컨벤션을 정비했습니다. 또한 숫자는 RTL 내에서 LTR로 표시되어야 하는 경우(`\u200e` LTR mark 삽입)도 있었습니다.

</details>

### Q2. 글로벌 서비스에서 국가별 날짜/통화/단위 포맷팅을 어떻게 처리했나요?
> **출제 의도**: 국제화(i18n)의 기술적 구현 깊이
>
> **경력 연관**: 이그나이트 딜러포탈 (48개국)

<details>
<summary><b>✅ 답변</b></summary>

**기본 원칙**: 브라우저 내장 `Intl` API를 최대한 활용하고, 커스텀 포맷터를 최소화했습니다.

**1) 날짜 포맷팅**:
```typescript
// 국가 코드 기반으로 locale 자동 결정
const formatDate = (date: Date, locale: string) =>
  new Intl.DateTimeFormat(locale, {
    year: 'numeric', month: 'long', day: 'numeric'
  }).format(date);

// 미국: "January 15, 2025"
// 독일: "15. Januar 2025"
// 한국: "2025년 1월 15일"
```

**2) 통화 포맷팅**:
- 금액은 항상 ISO 통화 코드(USD, EUR, KRW)와 함께 저장, 표시 시점에 포맷팅
- `Intl.NumberFormat`의 `style: 'currency'`로 통화 기호, 소수점, 구분자를 locale에 맞게 자동 처리

**3) 복수형 처리**: 언어마다 복수 규칙이 다릅니다(영어: 1개 vs 2개+, 러시아어: 1/2~4/5이상 3단계). `Intl.PluralRules` 또는 `i18next`의 `_plural`, `_1`, `_2` suffix로 복수형을 언어별로 정의했습니다.

**4) 단위 변환**: 차량 주행거리가 국가별로 km/miles로 달랐습니다. `Intl.MeasurementUnit`과 사용자 locale을 기반으로 자동 변환하되, 딜러 데이터는 항상 km로 저장하고 표시 시점에만 변환했습니다.

</details>

**꼬리 질문**:
- Intl API의 브라우저 지원 범위와 폴리필 전략은?
- 서버 사이드 렌더링에서 locale 처리는?
- 번역가가 placeholder가 포함된 문자열을 잘못 수정하는 문제는?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **Intl 폴리필**: `Intl.NumberFormat`, `Intl.DateTimeFormat`은 현대 브라우저에서 광범위하게 지원되지만, `Intl.PluralRules`나 `Intl.RelativeTimeFormat`은 구형 브라우저에서 누락될 수 있습니다. `@formatjs/intl-pluralrules` 폴리필을 동적으로 로드했습니다. 타겟 브라우저 범위를 정의하고 `browserslist`로 필요한 폴리필만 선택 로드하여 번들 크기를 최소화했습니다.

- **SSR locale 처리**: Next.js 미들웨어에서 `Accept-Language` 헤더와 URL 구조(`/en`, `/de`)를 조합하여 locale을 결정합니다. SSR 시점에 결정된 locale을 컴포넌트에 전달할 때, 서버/클라이언트 간 locale 불일치로 하이드레이션 미스매치가 발생하지 않도록 locale을 쿠키에 저장하고 서버와 클라이언트 모두 같은 쿠키 값을 읽도록 했습니다.

- **Placeholder 보호**: `{{vehicleName}}`처럼 이중 중괄호로 placeholder를 표시하고, CI에서 번역 파일을 검증할 때 원본의 placeholder가 번역에도 동일하게 존재하는지 확인합니다. 누락되거나 변형된 경우 CI 실패 + PR 코멘트로 번역가에게 알립니다. Phrase/Lokalise 같은 번역 플랫폼을 사용하면 placeholder를 잠금 처리할 수도 있었지만, 자체 구현으로도 충분했습니다.

</details>

### Q3. 기아 인증 중고차에서 접근성 점수 67 → 91로 개선한 방법을 설명해주세요.
> **출제 의도**: 웹 접근성 구현 실무 역량
>
> **경력 연관**: 기아 인증 중고차 (이그나이트)

<details>
<summary><b>✅ 답변</b></summary>

**초기 감사 결과**: Lighthouse Accessibility 점수 67. 주요 문제점을 카테고리별로 분류했습니다.

**1) 이미지 alt 텍스트 누락 (가장 큰 개선 포인트)**:
- 차량 이미지에 `alt=""`(장식용) 또는 `alt="차량 이미지"` 같은 비설명적 텍스트
- 차량명, 연식, 주행거리를 포함한 구체적인 alt 텍스트로 변경: `alt="2023 기아 K5 3.3 GTline 32,000km"`

**2) 색상 대비 미충족**:
- 차량 가격 표시의 회색 텍스트(`#999999`)가 흰 배경 대비 3.8:1 → WCAG AA 기준 4.5:1 미충족
- 디자이너와 협의하여 `#767676`으로 조정하여 4.5:1 이상 달성

**3) 키보드 네비게이션**:
- 차량 필터 드롭다운과 이미지 갤러리가 키보드로 조작 불가
- `onKeyDown`에 Enter/Space 처리, `tabIndex={0}` 추가
- 포커스 트랩: 모달 내에서 Tab 키가 모달 내부만 순환하도록 `focus-trap-react` 적용

**4) ARIA 레이블**:
- 아이콘 전용 버튼에 `aria-label` 추가
- 동적으로 업데이트되는 차량 목록 카운트에 `aria-live="polite"` 추가 (필터 변경 시 화면 낭독기가 카운트 변화를 읽어줌)

**5) 폼 레이블 연결**:
- 가격 범위 슬라이더의 input과 label이 `htmlFor`/`id`로 연결되지 않은 것 수정

**결과**: 67 → 91 (Lighthouse 기준). WCAG 2.1 AA 기준 주요 항목 통과.

</details>

**꼬리 질문**:
- WCAG 2.1 레벨 A, AA, AAA의 차이와 실무에서 어느 수준을 목표로 하나요?
- 스크린 리더로 실제 테스트한 경험이 있나요?
- 접근성 개선이 SEO에 미치는 영향은?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **WCAG 레벨 구분**: Level A는 최소 요건(alt 텍스트, 키보드 접근 등), Level AA는 일반적인 법적 요건(색상 대비 4.5:1, 캡션 등), Level AAA는 가장 엄격한 기준(9:1 대비율 등)입니다. 실무에서는 AA를 목표로 합니다. 한국은 「장애인차별금지법」에서 웹 접근성 준수를 요구하고, 글로벌 서비스는 ADA(미국), EAA(EU) 등 법적 요건이 있어 AA는 필수 수준입니다.

- **스크린 리더 테스트**: macOS VoiceOver(Safari)와 NVDA(Windows Chrome)로 주요 플로우(차량 검색 → 상세 → 문의)를 직접 탐색 테스트했습니다. Lighthouse가 잡지 못하는 문제들, 예를 들어 동적으로 업데이트되는 콘텐츠의 포커스 관리, 복잡한 컴포넌트의 role/aria-label 적절성 등을 확인했습니다. Jest + `@testing-library/jest-axe`로 자동화 테스트도 추가하여 회귀를 방지했습니다.

- **접근성과 SEO**: 직접적인 연관이 있습니다. alt 텍스트는 이미지 검색에 영향을 주고, 시맨틱 HTML(heading 계층, nav, main, article)은 검색 엔진이 콘텐츠 구조를 이해하는 데 도움이 됩니다. 색상 대비나 키보드 접근성은 SEO에 직접 영향은 없지만, 이탈률과 체류 시간을 통해 간접적으로 SEO 순위에 영향을 줄 수 있습니다. 기아 인증 중고차에서 접근성 개선 후 이탈률 18% 감소가 관측됐는데, 접근성이 좋아지면 더 많은 사용자가 불편 없이 탐색할 수 있어 체류 시간이 늘어나는 효과가 있었습니다.

</details>

### Q4. Datadog으로 프론트엔드를 어떻게 모니터링했나요?
> **출제 의도**: 관찰 가능성(Observability) 실무 경험
>
> **경력 연관**: 이그나이트 딜러포탈

<details>
<summary><b>✅ 답변</b></summary>

**Datadog RUM(Real User Monitoring) 활용**:

**1) 에러 모니터링**:
- 브라우저에서 발생하는 JS 에러를 자동 수집 (unhandled rejection 포함)
- 에러를 버전별, 브라우저별, 국가별로 필터링하여 특정 배포 이후 에러율 증가를 빠르게 탐지
- 에러 발생 직전 사용자 행동(Session Replay)을 재생하여 재현 시나리오 파악

**2) 인증 성공률 99.7% 측정**:
- 토큰 갱신 API 호출 수 vs 갱신 성공 수를 커스텀 메트릭으로 기록
- `datadogRum.addAction('token_refresh', { success: true/false })` 형태로 이벤트 전송
- 대시보드에서 실시간 성공률을 모니터링하고, 99% 미만 시 PagerDuty 알림 발송

**3) 성능 메트릭**:
- LCP, FID, CLS 등 Core Web Vitals를 실사용자 데이터(RUM)로 수집
- Lighthouse(시뮬레이션)와 RUM(실측) 데이터를 함께 보고, 특정 국가/네트워크에서 성능이 저하되는 케이스를 식별
- 배포 이후 LCP p75 값이 급등하면 자동 알림

**4) 비즈니스 메트릭 연동**:
- 딜러가 특정 기능을 사용하는 비율, 폼 완료율 등을 커스텀 이벤트로 트래킹
- 기능 개선 전후로 사용률 변화를 Datadog 대시보드에서 확인

</details>

**꼬리 질문**:
- Datadog RUM과 Sentry의 역할을 어떻게 구분했나요?
- Session Replay가 개인정보 관련 규정(GDPR)과 충돌하지 않나요?
- 커스텀 메트릭 설계 시 어떤 기준으로 무엇을 측정할지 결정했나요?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **Datadog vs Sentry 역할 구분**: Datadog RUM은 "무슨 일이 일어나고 있는가"를 실시간으로 보는 모니터링 관점입니다. 성능 추이, 에러율, 사용자 행동 패턴 등을 대시보드로 모니터링합니다. Sentry는 에러가 발생했을 때 "왜 일어났는가"를 파악하는 디버깅 관점입니다. Stack Trace, Context, Breadcrumb이 풍부하여 재현과 수정에 유리합니다. 에러가 발생하면 Datadog에서 트렌드를 파악하고, Sentry에서 원인을 분석하는 방식으로 병행 사용했습니다.

- **Session Replay와 GDPR**: GDPR 준수를 위해 두 가지 조치를 했습니다. 첫째, 개인정보가 포함될 수 있는 입력 필드(이름, 이메일, 전화번호)는 Datadog RUM SDK의 `privacyLevel: 'mask-user-input'` 설정으로 자동 마스킹했습니다. 둘째, Session Replay는 사용자 동의(ConsentGuard)를 받은 이후에만 활성화했습니다. EU 사용자에게는 명시적 동의를 받고, 동의 전에는 RUM 초기화 자체를 지연시켰습니다.

- **커스텀 메트릭 선택 기준**: "이 수치가 변하면 행동(Action)을 취할 것인가?"를 기준으로 삼았습니다. 토큰 갱신 성공률은 99% 미만이면 즉시 조사해야 하므로 모니터링 대상으로 선정했습니다. 반면 단순 페이지뷰 수는 Datadog 자동 수집으로 충분하여 커스텀 이벤트를 별도로 추가하지 않았습니다. 핵심 비즈니스 플로우(딜러 등록 완료, 차량 조회)의 완료율은 기능 개선 효과를 측정하는 기준으로 추가했습니다.

</details>

### Q5. 이탈률 18% 감소, 체류 시간 25% 증가를 어떻게 측정하고 달성했나요?
> **출제 의도**: 데이터 기반 성과 측정과 사용자 경험 개선 역량
>
> **경력 연관**: 기아 인증 중고차 (이그나이트)

<details>
<summary><b>✅ 답변</b></summary>

**측정 방법 (GA4 + 내부 BI)**:

- **이탈률(Bounce Rate)**: GA4에서 차량 상세 페이지 진입 후 추가 상호작용 없이 이탈한 세션 비율. 개선 전 약 62% → 개선 후 약 51%로 18% 감소 (51 / 62 = 82%, 즉 18% 감소)
- **체류 시간**: GA4의 `user_engagement` 이벤트 기반 평균 참여 시간. 개선 전 약 48초 → 60초로 25% 증가
- **A/B 비교**: 배포를 단계적(5% → 20% → 100%)으로 진행하면서 동일 기간 대조군과 비교하여 외부 요인의 영향을 통제했습니다

**달성 방법**:

**1) LCP 2.4s → 1.1s 개선**:
- 초기 로딩이 느리면 사용자가 페이지를 보기도 전에 이탈합니다. LCP 개선으로 첫 콘텐츠(차량 메인 이미지)가 빠르게 표시되어 이탈을 방지했습니다.

**2) 이미지 갤러리 UX 개선**:
- 기존: 한 장씩 로딩되어 스와이프 시 빈 화면이 노출
- 개선: 현재 이미지 기준 좌우 2장씩 미리 로딩(prefetch)하여 스와이프 시 즉시 표시. 더 많은 차량 사진을 볼 수록 체류 시간이 증가하는 효과

**3) 관련 차량 추천**:
- 상세 페이지 하단에 유사한 차량(동일 차종, 비슷한 가격대)을 추천하여 관심 차량이 없어도 페이지를 이탈하지 않고 다른 차량으로 이동하도록 유도

</details>

**꼬리 질문**:
- A/B 테스트 없이 이탈률 개선의 원인을 성능 개선으로 귀인하는 방법은?
- 이탈률이 낮아지는 것이 항상 긍정적인가요?
- 체류 시간과 전환율(CVR)이 상충하는 경우는?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **귀인 분석**: 완벽한 인과관계 증명은 A/B 테스트로만 가능합니다. 단계적 배포(Feature Flag로 5% → 100%)를 진행하면서 코호트 간 이탈률을 비교했습니다. 또한 외부 요인(계절성, 마케팅 캠페인)을 통제하기 위해 전년 동기 데이터와도 비교했습니다. LCP와 이탈률 간의 상관관계는 Google의 기존 연구와 일치하여 성능 개선이 주요 원인이라는 가설을 지지했습니다.

- **이탈률이 긍정적인 경우**: "이탈률이 낮으면 항상 좋다"는 오해가 있습니다. 사용자가 원하는 정보를 빠르게 찾고 만족하여 이탈하는 경우(예: FAQ 페이지에서 답변을 찾고 이탈)는 높은 이탈률이 오히려 긍정적입니다. 기아 인증 중고차 상세 페이지는 "이 차를 더 알아보고 싶다"는 의도의 방문이 많으므로, 이탈률 감소는 긍정적인 신호였습니다.

- **체류 시간 vs CVR 상충**: 체류 시간이 길어도 구매로 이어지지 않으면 의미가 없습니다. 이를 구분하기 위해 체류 시간을 "탐색 시간"과 "결정 시간"으로 분류했습니다. 차량 정보를 꼼꼼히 보는 탐색 행동(이미지 갤러리, 스펙 섹션 스크롤)은 긍정적이고, 문의 버튼 근처에서 오래 머무르는 것은 UX 문제의 신호로 해석했습니다. GA4의 scroll depth, click map 데이터를 함께 분석하여 구분했습니다.

</details>

### Q6. 동시 요청 50건을 큐잉 처리하며 인증 성공률 99.7%를 달성한 구체적 구현은?
> **출제 의도**: 비동기 요청 큐잉 및 동시성 제어 패턴
>
> **경력 연관**: 이그나이트 딜러포탈 MSA 인증

<details>
<summary><b>✅ 답변</b></summary>

**문제 상황**: 토큰 만료 시 동시에 50개의 API 요청이 401을 받으면, 각 요청이 독립적으로 토큰 갱신을 시도하여 Refresh Token이 50번 소비되는 문제 (일부 서버는 Refresh Token 1회만 허용).

**핵심 구현 - Promise 큐 + Mutex 패턴**:

```typescript
let isRefreshing = false;
let pendingRequests: Array<{
  resolve: (token: string) => void;
  reject: (error: unknown) => void;
}> = [];

const refreshTokenAndRetry = async (originalRequest) => {
  if (isRefreshing) {
    // 갱신 중이면 완료될 때까지 대기
    return new Promise((resolve, reject) => {
      pendingRequests.push({ resolve, reject });
    }).then((newToken) => retry(originalRequest, newToken));
  }

  isRefreshing = true;
  try {
    const newToken = await refreshAccessToken();
    // 대기 중인 모든 요청에 새 토큰 전달
    pendingRequests.forEach(({ resolve }) => resolve(newToken));
    return retry(originalRequest, newToken);
  } catch (error) {
    pendingRequests.forEach(({ reject }) => reject(error));
    throw error;
  } finally {
    isRefreshing = false;
    pendingRequests = [];
  }
};
```

**동작 흐름**:
1. 첫 번째 401 → `isRefreshing = true` → 토큰 갱신 시작
2. 그 후 들어오는 401 → `isRefreshing === true` → Promise로 대기 큐에 삽입
3. 갱신 완료 → 큐의 모든 Promise를 새 토큰으로 resolve → 대기 요청 일괄 재시도
4. 갱신 실패 → 큐의 모든 Promise를 reject → 로그인 리다이렉트

**이중 토큰 처리**: A 토큰 갱신 완료 후 B 토큰 재발급을 Promise 체인으로 순서 보장. B 토큰 재발급 실패 시에도 A 토큰은 유효하므로, B 토큰만 별도 재발급 시도.

**측정**: Datadog 커스텀 메트릭으로 401 발생 수, 재시도 성공 수, 최종 실패 수를 기록하여 99.7% 성공률 확인.

</details>

**꼬리 질문**:
- `isRefreshing` 플래그를 모듈 레벨에서 관리할 때의 문제점은?
- 토큰 갱신이 5초 이상 걸릴 때 대기 중인 요청에 어떻게 처리했나요?
- 멀티 탭 환경에서 같은 문제가 발생하지 않나요?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **모듈 레벨 플래그 문제**: 싱글톤처럼 동작하여 여러 HTTP 클라이언트 인스턴스가 존재할 때 각자 독립된 `isRefreshing`을 가지면 중복 갱신이 발생할 수 있습니다. 이를 방지하기 위해 토큰 갱신 로직을 전역 싱글톤 모듈로 분리하여 모든 클라이언트 인스턴스가 같은 갱신 로직을 참조하도록 했습니다. React Query의 `QueryClient`도 싱글톤으로 관리하여 일관성을 유지했습니다.

- **장시간 대기 처리**: 토큰 갱신 요청에 타임아웃(10초)을 설정했습니다. 타임아웃 시 갱신 실패로 처리하고 큐를 비웠습니다. 대기 중인 요청이 오래 걸리면 사용자에게 로딩 인디케이터가 표시되는데, 갑작스러운 느림 현상을 방지하기 위해 토큰 만료 예상 시간(exp 클레임 기반) 이전에 미리 갱신하는 Proactive Refresh를 구현했습니다. 만료 5분 전에 백그라운드 갱신을 시작하여 사용자가 요청을 보낼 때는 항상 유효한 토큰이 준비된 상태를 유지했습니다.

- **멀티 탭 문제**: 탭 A에서 토큰을 갱신하고 탭 B도 거의 동시에 갱신을 시도하면 Refresh Token이 중복 사용될 수 있습니다. `BroadcastChannel` API를 활용하여 한 탭에서 토큰 갱신이 완료되면 다른 탭에도 새 토큰을 브로드캐스트했습니다. 다른 탭은 새 토큰을 수신하면 갱신 시도 없이 해당 토큰을 사용합니다. 서버 측에서도 Refresh Token Rotation과 짧은 Reuse Interval을 설정하여 중복 사용 시 이전 토큰도 무효화하는 방어 로직을 두었습니다.

</details>
