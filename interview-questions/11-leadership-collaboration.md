# 리더십 & 협업 질문

### Q1. 프로젝트 리딩에서 코드 리뷰, 기술 방향 설정, 스프린트 관리를 어떻게 수행했나요?
> **출제 의도**: 테크 리드 역할의 실행력
>
> **경력 연관**: 이그나이트 딜러포탈

<details>
<summary><b>✅ 답변</b></summary>

**코드 리뷰**:
- PR 리뷰 기준을 문서화: 비즈니스 로직 정확성 > 성능 > 코드 스타일 순으로 우선순위
- 단순 스타일 지적보다 "왜"를 설명하는 리뷰 문화. 링크/사례 첨부로 교육적 리뷰
- 리뷰 응답 시간 24시간 이내 목표 (슬랙 알림 커스텀 액션 활용)

**기술 방향 설정**:
- 분기별 기술 로드맵 수립: 성능 최적화, 모노레포 안정화, 테스트 커버리지 등 기술 부채 해소 계획
- 새 기술 도입 시 RFC(Request for Comments) 문서를 작성하여 팀 합의 후 진행
- 기술 선택 기준: 팀 러닝 커브, 유지보수성, 커뮤니티 활성도

**스프린트 관리**:
- 2주 스프린트, JIRA 기반 태스크 분배
- 스프린트 플래닝에서 각 태스크의 스토리 포인트를 팀이 함께 산정
- 데일리 스탠드업에서 블로커 확인, 스프린트 리트로에서 개선점 도출

**팀 규모**: 프론트엔드 6명. 주니어 개발자가 있어 기술 멘토링 역할도 병행.

</details>

### Q2. 신입 개발자 멘토링 경험과 온보딩 프로세스를 설명해주세요.
> **출제 의도**: 멘토링 및 팀 성장 기여 역량
>
> **경력 연관**: 마이리얼트립 통합숙소 / 디자인시스템

<details>
<summary><b>✅ 답변</b></summary>

**멘토링 방식**:

1. **페어 프로그래밍**: 주 2~3회 함께 코딩하며 실시간으로 설계 결정의 이유를 설명. 단순히 "이렇게 해"가 아닌 "이렇게 하는 이유"를 전달
2. **코드 리뷰 기반 학습**: PR 리뷰에서 패턴, 안티패턴을 짚어주고 관련 문서/블로그 링크 제공
3. **점진적 난이도 상승**: 버그 수정 → 작은 기능 → 독립 기능 → 설계부터 맡기기 순서로 성장 경로 설계

**디자인시스템 QA 프로세스 정립**:
- 신입 개발자와 함께 QA 체크리스트를 만들고, 반복적인 QA 작업을 경험하면서 컴포넌트 품질 기준을 체득
- Storybook의 Visual Regression Test 도입으로 UI 변경을 자동 감지

**온보딩 자동화**:
- DX Script TF에서 온보딩 셋업 스크립트를 만들어 환경 설정 시간 2시간 → 15분으로 단축
- "Storybook 보면서 작업하세요" → 컴포넌트 카탈로그로 팀의 UI 패턴을 빠르게 파악

**성과**: 신입 개발자가 2주 내에 첫 PR을 생성하고, 1개월 내에 독립적으로 기능 개발이 가능한 수준으로 성장.

</details>

### Q3. 관리자 부재 상태의 레거시 코드를 인수하여 현대화한 경험을 설명해주세요.
> **출제 의도**: 레거시 코드 인수 및 기술 부채 해소 전략
>
> **경력 연관**: 마이리얼트립 렌터카/숙소 고도화

<details>
<summary><b>✅ 답변</b></summary>

**상황**: 숙소/렌터카 도메인의 기존 담당자가 퇴사한 상태. 코드 문서 없음, 테스트 없음, 비즈니스 로직이 컴포넌트에 산재.

**인수 과정**:
1. **코드 분석 (2주)**: 전체 코드를 읽으며 비즈니스 플로우를 파악. 주요 로직에 주석 추가
2. **리스크 파악**: Sentry 에러 로그, JIRA 버그 티켓을 분석하여 가장 빈번한 문제 영역 식별
3. **로드맵 수립**: 긴급(에러 수정) → 중요(아키텍처 개선) → 일반(리팩토링) 순으로 우선순위 설정

**점진적 현대화**:
- **useEffect 정리**: 컴포넌트당 평균 3.7개 → 0.7개. 단방향 데이터 플로우로 재구성
- **Redux → React Query**: 서버 상태를 React Query로 마이그레이션하여 보일러플레이트 60% 제거
- **Suspense + ErrorBoundary**: 선언적 에러 핸들링으로 빈 화면 문제 해결
- **LocalStorage 어댑터**: 버전 관리 가능한 어댑터로 스키마 변경 시 하위 호환성 보장

**교훈**: 레거시 코드를 한 번에 전면 교체(Big Rewrite)하는 것보다 점진적으로 개선(Incremental Improvement)하는 것이 리스크가 낮습니다. 기존 기능이 정상 동작하는 상태를 유지하면서, 영역별로 교체하는 Strangler Fig 패턴을 적용했습니다.

</details>

### Q4. 6개 프로덕트 팀에 디자인 시스템을 제공하면서 팀 간 요구사항을 어떻게 조율했나요?
> **출제 의도**: 크로스 팀 커뮤니케이션 역량
>
> **경력 연관**: 마이리얼트립 디자인시스템

<details>
<summary><b>✅ 답변</b></summary>

**조율 프로세스**:

1. **월 1회 디자인 시스템 싱크 미팅**: 각 팀의 요구사항을 수집하고, 우선순위를 함께 결정
2. **범용/도메인 분류 기준**:
   - **디자인 시스템에 포함**: 3개 팀 이상에서 사용하는 컴포넌트
   - **각 팀 프로젝트에 유지**: 도메인 특화 컴포넌트 (예: 호텔 객실 선택기)
3. **RFC 프로세스**: 새 컴포넌트 제안 시 사용 사례, API 설계, 디자인 시안을 문서화하여 팀 피드백 수렴

**갈등 해결 사례**:
- 한 팀에서 Button 컴포넌트에 특수 variant를 요구했으나, 다른 팀에서는 불필요하다고 반대
- 해결: `variant` prop은 범용 옵션만 유지하고, `className` prop을 통한 스타일 오버라이드를 허용. 특수 variant는 해당 팀에서 래핑 컴포넌트로 구현

**Breaking Change 관리**: MAJOR 업데이트 시 2주간 이전 버전을 유지하고, 마이그레이션 가이드를 CHANGELOG에 포함. 팀별 마이그레이션 일정을 협의하여 일괄 전환 부담을 분산.

</details>

### Q5. 기술 도입 결정 시 어떤 기준으로 판단하나요?
> **출제 의도**: 기술 선택의 판단력
>
> **경력 연관**: 전체 경력

<details>
<summary><b>✅ 답변</b></summary>

**5가지 기준**:

1. **문제 적합성**: 현재 문제를 실제로 해결하는가? "좋은 기술"이 아닌 "적합한 기술"을 선택
2. **팀 러닝 커브**: 팀 전체가 합리적인 시간 내에 습득할 수 있는가? 한 사람만 사용할 수 있는 기술은 버스 팩터 리스크
3. **유지보수성**: 커뮤니티가 활성화되어 있는가? 문서가 잘 되어 있는가? 메인테이너가 적극적인가?
4. **마이그레이션 비용**: 기존 코드와의 호환성, 점진적 도입 가능 여부
5. **측정 가능한 개선**: 도입 전후를 정량적으로 비교할 수 있는가? (성능 수치, 코드 라인 수, 에러 발생률 등)

**실제 사례**:
- **React Query 도입 (채택)**: Redux의 서버 상태 관리 보일러플레이트 문제 해결, 점진적 마이그레이션 가능, 커뮤니티 활성
- **XState 검토 (미채택)**: 상태 머신 패턴에 적합하지만, 20단계 폼 하나에만 필요했고, 팀 전체 학습 비용 대비 효과가 낮아 `useReducer`로 대체

**의사결정 프로세스**: 
1. 문제 정의 → 2. 후보 기술 3개 이내 선정 → 3. PoC 작성 → 4. RFC 문서화 → 5. 팀 리뷰 → 6. 결정

</details>

### Q6. 블로그 활동이 업무에 어떤 영향을 주었나요?
> **출제 의도**: 지식 공유와 커뮤니티 기여 자세
>
> **경력 연관**: zigae.com 블로그

<details>
<summary><b>✅ 답변</b></summary>

**블로그 활동 (zigae.com)**:

1. **지식 정리 효과**: 트러블슈팅 과정을 글로 정리하면서 이해가 더 깊어지고, 비슷한 문제 재발 시 빠르게 참조할 수 있었습니다.
2. **팀 내 공유**: validateDOMNesting 해결 사례를 블로그에 정리하여 팀원들에게 공유. 비슷한 패턴의 문제를 사전에 방지
3. **커뮤니티 피드백**: 글에 대한 댓글과 피드백으로 더 나은 해결 방법을 배우는 경우도 있었습니다

**오픈소스 기여와의 연결**: 블로그에 정리한 이슈가 오픈소스 라이브러리의 버그인 경우 PR로 연결되기도 했습니다. @tanstack/react-virtual 이슈도 블로그 정리 과정에서 라이브러리 코드까지 분석하게 되어 PR을 제출하게 된 계기였습니다.

</details>
