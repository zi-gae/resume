# 모노레포 & 아키텍처 질문

### Q1. Turborepo 기반 모노레포에서 3개 브랜드(현대/기아/제네시스) 포탈이 공통 컴포넌트/훅/유틸을 공유하는 구조를 설명해주세요.
> **출제 의도**: 대규모 모노레포 설계 역량
>
> **경력 연관**: 이그나이트 딜러포탈

<details>
<summary><b>✅ 답변</b></summary>

**디렉토리 구조**:
```
apps/
  hyundai-portal/    # 현대 딜러 포탈
  kia-portal/        # 기아 딜러 포탈
  genesis-portal/    # 제네시스 딜러 포탈
packages/
  ui/                # 공통 UI 컴포넌트 (Button, Modal, Table 등)
  hooks/             # 공통 커스텀 훅 (useAuth, useQueryParams 등)
  utils/             # 공통 유틸리티 (날짜 포맷, 통화 변환 등)
  config/            # ESLint, TSConfig 등 공유 설정
  tokens/            # 디자인 토큰 (브랜드별 CSS 변수)
```

**핵심 설계 원칙**:
1. **브랜드 분기는 토큰 레벨에서만**: 컴포넌트 코드는 동일하고, CSS 변수 값만 브랜드별로 다르게 주입. `--color-brand-primary`가 현대에서는 파란색, 기아에서는 빨간색
2. **Internal Packages**: `packages/*`는 npm 배포 없이 workspace 내부에서 직접 참조. 빌드 없이 소스 코드를 직접 import하여 변경 즉시 반영
3. **의존성 방향 강제**: `apps → packages` 방향만 허용, `packages` 간 순환 참조 금지. Turborepo의 `dependsOn` 설정으로 빌드 순서 보장

**Turborepo 활용**:
- `turbo run build --filter=hyundai-portal...`: 변경된 패키지와 그 의존자만 빌드
- Remote Caching으로 CI에서 빌드 캐시 공유. 동일 입력이면 빌드 스킵
- `turbo.json`에서 태스크 파이프라인 정의: `build → test → lint` 순서와 병렬 실행 규칙

</details>

**꼬리 질문**:
- 모노레포에서 패키지 간 버전 관리는 어떻게?
- 한 패키지 변경이 다른 앱에 영향을 주는 것을 어떻게 방지?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **버전 관리**: Internal Packages이므로 npm 버전 관리가 필요 없습니다. `package.json`에서 `"@repo/ui": "workspace:*"`로 참조하면 항상 최신 소스를 직접 사용합니다. 외부 배포가 필요한 패키지가 있다면 Changesets로 독립 버전 관리를 합니다.

- **영향 범위 제한**: Turborepo의 변경 감지(`--filter=...[HEAD^]`)로 변경된 패키지의 의존자만 빌드/테스트합니다. PR에서 `packages/ui` 변경 시 3개 앱 모두의 빌드와 테스트가 자동 실행되어, 머지 전에 영향을 확인합니다. 또한 `packages/ui`에 대한 단위 테스트가 있어 패키지 레벨에서 먼저 검증됩니다.

</details>

### Q2. 마이리얼트립에서 FE 공통 모듈 모노레포를 구축하여 8개 프로젝트에서 공유한 경험을 설명해주세요.
> **출제 의도**: 공통 모듈 설계와 조직 내 표준화 역량
>
> **경력 연관**: 마이리얼트립 FE libs TF

<details>
<summary><b>✅ 답변</b></summary>

**배경**: 8개 프로젝트에서 인증, API 클라이언트, 유틸리티 함수 등을 각자 구현하여 코드 중복과 동작 불일치 발생.

**구축 과정**:
1. **공통 모듈 식별**: 각 프로젝트의 코드를 분석하여 중복되는 로직을 카테고리별로 분류 (인증, HTTP, 날짜, 통화, 트래킹 등)
2. **모노레포 구조 설계**: 각 카테고리를 독립 패키지로 분리하여 필요한 것만 설치 가능하도록 구성
3. **점진적 마이그레이션**: 각 프로젝트가 자체 구현을 공통 모듈로 교체. 기존 인터페이스와 호환되는 API 설계

**Barrel 파일 순환 참조 이슈**:
- 문제: `index.ts`(Barrel 파일)를 통한 re-export에서 패키지 간 순환 참조 발생. Lint + Jest 실행 시 모듈 해석 인스턴스가 무한 생성되어 12분+ 소요
- 진단: CI 로그에서 메모리 사용량이 비정상적으로 증가하는 구간 확인 → 모듈 해석 트레이스로 순환 경로 파악
- 해결: Barrel 파일 제거 + 직접 import 경로 사용 (`@mrt/utils` → `@mrt/utils/date`). 빌드/테스트 시간 12분 → 5분으로 단축

</details>

### Q3. MSA 기반 서브도메인 프론트엔드 아키텍처는 어떻게 설계했나요?
> **출제 의도**: 마이크로 프론트엔드 설계 경험
>
> **경력 연관**: 마이리얼트립 통합숙소

<details>
<summary><b>✅ 답변</b></summary>

**아키텍처**: MSA 백엔드에 맞춰 프론트엔드도 서브도메인별로 분리된 Next.js 애플리케이션으로 구성했습니다.

```
stays.myrealtrip.com     → 숙소 Next.js 앱
tours.myrealtrip.com     → 투어 Next.js 앱
rentcar.myrealtrip.com   → 렌터카 Next.js 앱
```

**설계 원칙**:
1. **독립 배포**: 각 서브도메인 앱이 독립적으로 빌드/배포. 숙소팀의 배포가 렌터카팀에 영향 없음
2. **공유 레이어**: 인증, GNB, 결제 모듈 등 공통 기능은 npm 패키지로 공유
3. **API Gateway 패턴**: 프론트엔드에서 직접 마이크로서비스를 호출하지 않고, BFF(Backend For Frontend)를 통해 필요한 데이터를 조합

**프론트엔드 모듈 간 의존성 관리**:
- 서브도메인 간 네비게이션은 `window.location.href`로 전체 페이지 전환 (SPA 라우팅이 아닌 별도 앱이므로)
- 공유 상태는 쿠키 기반 (인증 토큰, 사용자 설정 등)
- 공통 이벤트 트래킹은 npm 패키지로 통합하여 일관된 분석 데이터 확보

</details>

**꼬리 질문**:
- 마이크로 프론트엔드와 모노레포의 차이점은?
- 서브도메인 간 데이터 공유 방법은?

<details>
<summary><b>✅ 꼬리 답변</b></summary>

- **차이점**: 모노레포는 코드 저장소 관리 전략(하나의 repo에 여러 프로젝트), 마이크로 프론트엔드는 런타임 아키텍처(독립 배포된 앱들이 하나의 화면을 구성). 둘은 독립된 개념으로, 모노레포이면서 마이크로 프론트엔드일 수도 있고, 멀티레포이면서 모놀리식일 수도 있습니다. 마이리얼트립에서는 모노레포 + 서브도메인 분리(경량 마이크로 프론트엔드)를 함께 사용했습니다.

- **데이터 공유**: 인증 토큰은 상위 도메인(`.myrealtrip.com`) 쿠키에 저장하여 서브도메인 간 공유. 장바구니 같은 사용자 상태는 서버 API를 통해 동기화. 실시간 공유가 필요한 경우(로그인/로그아웃 시 다른 탭 반영)는 `BroadcastChannel API`를 활용했습니다.

</details>

### Q4. PHP/jQuery → React/Next.js 전환 프로젝트에서의 점진적 마이그레이션 전략을 설명해주세요.
> **출제 의도**: 레거시 마이그레이션 전략과 실행력
>
> **경력 연관**: 브랜디 커머스 플랫폼

<details>
<summary><b>✅ 답변</b></summary>

**전략: Strangler Fig 패턴**

기존 PHP 서비스를 유지하면서 새로운 페이지부터 Next.js로 개발하고, 점진적으로 교체하는 방식입니다.

```
Phase 1: 신규 페이지를 Next.js로 개발, Nginx에서 URL 기반 라우팅
Phase 2: 핵심 페이지(상품 상세, 결제) Next.js 전환
Phase 3: 남은 페이지 전환 + PHP 서비스 제거
```

**Nginx 라우팅**:
```
/products/*  → Next.js (전환 완료)
/checkout/*  → Next.js (전환 완료)
/legacy/*    → PHP (미전환)
```

**주요 과제와 해결**:
1. **세션 공유**: PHP 세션과 Next.js 간 인증 상태 공유를 위해, PHP 세션 ID를 쿠키에 저장하고 Next.js에서 API를 통해 세션 검증
2. **UI 일관성**: 전환 과정에서 PHP 페이지와 Next.js 페이지의 디자인이 달라 보이지 않도록 동일한 CSS 프레임워크(Bootstrap) 사용 후 점진적으로 Emotion 전환
3. **Docker + AWS ECS/Fargate**: Next.js 앱을 컨테이너화하여 기존 인프라와 분리 배포

</details>

### Q5. 온보딩 자동화 스크립트로 셋업 시간을 2시간에서 15분으로 단축한 경험을 설명해주세요.
> **출제 의도**: 개발자 경험(DX) 개선 역량
>
> **경력 연관**: 마이리얼트립 DX Script TF

<details>
<summary><b>✅ 답변</b></summary>

**배경**: 신규 입사자가 개발 환경을 셋업하는 데 평균 2시간 소요. README 문서가 분산되어 있고, 환경마다 설정이 달라 실패 케이스가 빈번.

**스크립트 구성**:
1. **환경 의존성 설치**: Node.js(nvm), yarn, Docker, AWS CLI 등 필수 도구 설치 + 버전 검증
2. **저장소 클론 + 의존성 설치**: 프로젝트별 저장소 클론, yarn install, 환경변수 설정
3. **로컬 서비스 실행**: Docker Compose로 로컬 DB, Redis 등 의존 서비스 기동
4. **검증**: 각 프로젝트의 빌드와 테스트가 통과하는지 자동 확인

**실측 결과**: 온보딩 리트로 5회 실측 평균 2시간 → 15분으로 단축. 신규 입사자가 첫날 오전에 코드를 실행할 수 있는 환경이 됨.

**핵심 설계**: 멱등성(Idempotent) 보장. 스크립트를 여러 번 실행해도 동일한 결과. 이미 설치된 도구는 건너뛰고, 버전이 다르면 경고 표시.

</details>

### Q6. 깃허브 액션 슬랙 알림 커스텀 액션을 만들어 Marketplace에 배포한 경험은?
> **출제 의도**: CI/CD 자동화 및 오픈소스 기여
>
> **경력 연관**: 마이리얼트립 Actions TF

<details>
<summary><b>✅ 답변</b></summary>

**동기**: 기존 슬랙 알림 액션들이 마이리얼트립의 워크플로우(PR 리뷰 요청, 배포 완료, 빌드 실패 등)에 맞지 않아 커스텀 필요.

**구현**:
1. **JavaScript Action**으로 개발 (Docker Action 대비 실행 속도 빠름)
2. **이벤트별 메시지 포맷**: PR 생성, 리뷰 요청, 머지, 배포 등 이벤트별로 다른 슬랙 메시지 템플릿
3. **컨텍스트 정보 포함**: PR 작성자, 변경 파일 수, 빌드 로그 링크 등 개발자에게 필요한 정보를 슬랙 메시지에 포함

**Marketplace 배포**: GitHub Marketplace에 공개하여 사내뿐 아니라 외부 개발자도 사용할 수 있도록 배포. 문서와 예제 코드를 포함한 README 작성.

**성과**: PR 리뷰 응답 시간 단축 (슬랙에서 바로 PR 링크 확인), 배포 실패 시 즉각 알림으로 대응 시간 단축.

</details>
